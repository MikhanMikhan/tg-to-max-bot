# Social Network Factory — дублирование постов Telegram → MAX

Система дублирует посты из Telegram-каналов в MAX-каналы с отложенной
публикацией. Один экземпляр бота обслуживает много пар «TG-канал → MAX-канал»
(связок). Терминология — в `CONTEXT.md`.

## Как это работает

1. Владелец канала подключает связку в личке с ботом (см. «Подключение своего
   канала» ниже). Посты из неподключённых каналов игнорируются.
2. Бот (админ TG-канала) получает новые посты и правки через long-polling Bot API.
3. Каждый пост кладётся в очередь (SQLite, `queue.db`) с `publish_at = now + delay`
   связки (по умолчанию 60 минут).
4. Бот пишет владельцу связки в личку: «Дубль выйдет в HH:MM DD.MM…». Ответьте
   **реплаем** на это сообщение другим временем, чтобы перенести: `18:00`,
   `завтра 15:30`, `послезавтра 8:00`, `10.08 12:00`, `01.09.2026 07:45`.
   Молчание = дефолт.
5. Планировщик (тик 30 с) публикует просроченные записи в MAX-канал связки:
   скачивает медиа из Telegram, загружает в MAX (`POST /uploads` → файл →
   `POST /messages`).
6. Правки поста до публикации дубля обновляют сохранённый слепок; правки после
   публикации игнорируются. Удаления Bot API не присылает — пост, удалённый до
   выхода дубля, всё равно будет продублирован (принятая оговорка).
7. Сбой публикации → повтор через 5 мин, затем 30 мин; после 3-й неудачной
   попытки статус `failed` и уведомление владельцу в личку. Пропущенные за простой
   посты догоняются: Telegram пришлёт их через getUpdates при старте
   (дубликаты отсекаются уникальным ключом `chat_id + message_id`), а
   просроченные записи очереди публикует тот же планировщик.

## Подключение своего канала

Один бот обслуживает много связок «TG-канал → MAX-канал». Чтобы подключить свою:

1. Добавьте этого Telegram-бота **администратором** вашего TG-канала.
2. Добавьте MAX-бота **администратором** вашего MAX-канала.
3. Напишите боту в личку `/start` и **перешлите ему любой пост** из вашего
   TG-канала. Бот проверит, что админами канала являетесь и вы, и он (иначе
   связку подключить нельзя — защита от чужих каналов).
4. Пришлите id вашего MAX-канала (число вида `-72075083149532` или ссылку).
   Бот проверит доступность канала через MAX API и подтвердит подключение.

Готово — новые посты будут дублироваться автоматически. Команды в личке:

- `/status` — список ваших связок (каналы, задержка, активность);
- `/disconnect <tg_channel_id>` — отключить связку (ожидавшие публикации
  дубли отменяются). Если связка одна, id можно не указывать.

Альбомы (media_group) собираются в один дубль: ждём ~2 с после последнего
сообщения группы и регистрируем один пост с дедупликацией по `media_group_id`.

**Молчаливая деградация**: опросы, inline-кнопки, спойлеры, упоминания и прочее,
не переносимое в MAX, молча отбрасывается. Разметка маппится в MAX-markdown:
bold → `**`, italic → `*`, underline → `++`, strikethrough → `~~`, code/pre →
`` ` ``, ссылки → `[текст](url)`.

## Установка

Требуется Python 3.11+.

```bash
python -m venv .venv
# Windows (Git Bash):
.venv/Scripts/python.exe -m pip install -r requirements.txt
# Linux/macOS:
.venv/bin/pip install -r requirements.txt
```

## Получение токенов

### Telegram
1. В [@BotFather](https://t.me/BotFather): `/newbot`, получите токен → `TELEGRAM_BOT_TOKEN`.
2. Добавьте бота **администратором** вашего канала (права на чтение постов достаточно — бот получает `channel_post` автоматически).
3. Напишите боту в личку `/start` и подключите связку (см. «Подключение своего канала»).

### MAX
1. Зарегистрируйтесь на [business.max.ru](https://business.max.ru) и пройдите
   верификацию (самозанятый / ИП / юрлицо РФ).
2. Создайте чат-бота (платформа «Чат-боты» → «Перейти» → «Расширенные настройки» → «Настроить»,
   либо мини-приложение «MAX для бизнеса» → «Получить токен») → `MAX_BOT_TOKEN`.
3. Создайте канал в MAX и добавьте бота в канал. Его `chat_id` вводится при
   подключении связки в личке бота — отдельно настраивать не нужно.

## Переменные окружения (`.env`)

```bash
cp .env.example .env
```

| Переменная | Описание |
|---|---|
| `TELEGRAM_BOT_TOKEN` | токен TG-бота от BotFather (обязательно) |
| `MAX_BOT_TOKEN` | токен MAX-бота |
| `MAX_CHANNEL_ID` | legacy: chat_id канала в MAX, используется только для миграции существующей БД в связку при первом запуске |
| `DEFAULT_DELAY_MINUTES` | задержка дубля по умолчанию, минут (60) |
| `TZ` | часовой пояс, напр. `Europe/Moscow` |
| `ADMIN_TG_USER_ID` | TG user id оператора бота — включает команды `/admin` (все связки с числом ожидающих дублей) и `/admin_disconnect <id>` (принудительное отключение чужой связки с уведомлением владельца). `0`/пусто — команды отключены |

`.env` не коммитится (в `.gitignore`).

### Режим без настроенного MAX

Если `MAX_BOT_TOKEN` пуст, приложение работает, но регистрация связок и
публикация заглушены: при наступлении `publish_at` запись переводится в
`failed` с причиной «MAX не настроен (пустой MAX_BOT_TOKEN)», владельцу
приходит уведомление в личку. Так можно проверить приём постов и очередь до
получения доступа к MAX API.

## Запуск

```bash
# Windows (Git Bash):
.venv/Scripts/python.exe -m app.bot

```

## Перенос архива старых постов (backfill)

Bot API историю канала не отдаёт, поэтому архив переносится отдельным скриптом
из **экспорта Telegram Desktop** (меню канала → «Экспорт истории чата»).
Поддерживаются оба формата экспорта: машиночитаемый JSON (`result.json`) и
человекочитаемый HTML (`messages.html`) — что есть в папке, то и используется.
При экспорте включайте скачивание медиа (фото/видео), иначе такие посты будут
пропущены с пометкой в логе.

Запуск:

```bash
# сначала проверочный прогон без публикации (токены MAX не нужны):
.venv/Scripts/python.exe -m app.backfill --export-dir "путь/к/экспорту" --dry-run
# реальный перенос:
.venv/Scripts/python.exe -m app.backfill --export-dir "путь/к/экспорту" --interval 60 --limit 10
```

Скрипт идёт от старых постов к новым, публикует в MAX по одному посту с
интервалом (по умолчанию 60 мин, или `BACKFILL_INTERVAL_MINUTES` в `.env`) и
пишет прогресс в `backfill_state.json` — можно прервать (Ctrl+C) и продолжить
позже с того же места. Разметка конвертируется в MAX-markdown тем же кодом,
что и в основном пайплайне. Альбомы собираются в один пост (в JSON — по
`grouped_id`, в HTML — по joined-сообщениям), служебные сообщения
пропускаются. Непереносимое (опросы, реакции и т.п.) молча отбрасывается;
медиа, не скачанное при экспорте («Not included...»), пропускается.

Устаревшие посты (анонсы прошедших мероприятий, истёкшие акции) не переносятся:
их id перечислены в `backfill_skip.json` (`skip_ids`), скрипт пропускает их
с пометкой в логе. Файл необязателен.

## Структура

Проект разделён на два модуля с общим ядром:

```
app/
  core/               # общий код обоих модулей
    content.py        # слепок поста + маппинг TG entities → MAX markdown
    max_client.py     # MAX Bot API на httpx: POST /uploads, POST /messages
  bot/                # модуль 1: бот дублирования (python -m app.bot)
    config.py         # конфиг из .env
    db.py             # очередь в SQLite (posts, tenants, registration_state), дедупликация
    timeparse.py      # парсинг «завтра 15:30» и т.п.
    backoff.py        # интервалы ретраев: 5 мин → 30 мин, max 3 попытки
    albums.py         # сборка media_group в один дубль (задержка 2 с)
    telegram_side.py  # хендлеры aiogram: посты, правки, диалог с автором
    tg_session.py     # aiohttp-сессия aiogram (прокси/SSL)
    scheduler.py      # asyncio-цикл (тик 30 с): публикация, ретраи, уведомления
    main.py           # точка входа
  backfill/           # модуль 2: перенос архива канала (python -m app.backfill)
    tgexport_html.py  # парсер HTML-экспорта Telegram Desktop (messages.html)
    cli.py            # перенос архива канала в MAX (JSON или HTML экспорт)
tests/                # pytest, без сети
```

## Известные ограничения

- Voice из Telegram переносится как `audio`.
- Вложение `file` в MAX нельзя комбинировать с image/video — TG-альбомы из
  фото/видео переносятся, документы идут отдельными постами (как и в TG).
- Один альбом = до 12 вложений в MAX; TG-альбомы (≤10) укладываются.

## Деплой на VPS

Пример развёртывания на VPS (Ubuntu, Python 3.12): systemd-сервис `snf-bot`
из `/opt/snf`. Портов не занимает (long-polling TG + исходящие MAX), Docker
не используется.

Разовая подготовка сервера:

```bash
# локально: залить код, затем на сервере
bash deploy/server-setup.sh     # venv, pip install, systemd unit, logrotate
# положить /opt/snf/.env (токены), при миграции — queue.db и backfill_state.json
systemctl start snf-bot
```

Обновление кода — `DEPLOY_HOST=user@host bash deploy/deploy.sh` из корня
проекта (Git Bash):
заливает `app/`, `certs/`, `requirements.txt`, ставит зависимости и
перезапускает сервис. Состояние (`queue.db`, `backfill_state.json`, `.env`)
на сервере не перезаписывается.

**Важно:** Telegram getUpdates допускает только одного long-polling'ера на
токен — перед запуском на сервере локальные задачи (`main_task.bat`,
`backfill_task.bat` в Планировщике заданий) должны быть остановлены.

Логи: `journalctl -u snf-bot -f` (stdout) и `/opt/snf/main.log` (лог
приложения, ротация — logrotate, weekly/4).
